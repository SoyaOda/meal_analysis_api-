食品名意味的マッチングシステム：ベクトル検索＋LLM再ランキング 技術仕様書
システム概要

目的: 本システムは、食品画像認識で得られた食品名（search_name）および追加の説明テキスト（description）から、USDA準拠の食品データベース（約1,000〜10,000件のエントリ）内で最も意味的に対応する食品エントリを特定することを目的としています。食品名の表記揺れや類義語（例：「フライドポテト」と「フレンチフライ」）に対応し、ユーザーが意図する食品を高精度にマッチングする柔軟な検索を実現します。

全体アーキテクチャ: 意味的マッチングには「ベクトル検索（ANN）＋LLM再ランキング」の二段階アプローチを採用します
deepinfra.com
。まず第1段階でクエリ（食品名＋説明）を埋め込みベクトルに変換し、ベクトル類似度検索によって候補食品エントリを絞り込みます（高速な近似最近傍検索により数百万件の中からミリ秒で上位候補を取得可能
deepinfra.com
）。次に第2段階として、上位候補（例：5〜10件）を大規模言語モデル（LLM）に渡し、クエリとの文脈・意味合いを精査して最も適切なマッチを1件選出します
deepinfra.com
adasci.org
。このハイブリッド構成により、検索の網羅性と精度を両立し、ユーザーにとって「探している食品」が確実にヒットすることを目指します。
ベクトル検索（第1段階）
埋め込みモデルの選定とベストプラクティス

ベクトル検索の精度はベクトル化（Embedding）モデルに大きく依存します。以下の選択肢を検討し、要件に合ったモデルを採用します。

    汎用事前学習モデル: 一般的な意味表現に優れたSentence-BERT系列のモデルが有力です。例えば、all-MiniLM-L6-v2（Dim=384）は高速かつ軽量で広範な語彙に対応し、検索レスポンスを重視する場合に適しています。一方、精度重視ならばall-mpnet-base-v2（Dim=768）など大きめのモデルが候補です。これら汎用モデルはオープンソースで入手容易かつ多目的なセマンティック検索で実績があります。

    食品ドメイン特化モデル: 食品名固有のニュアンス（料理名、材料名など）に注目するにはドメインに特化した埋め込みモデルも有効です。例えば、食品レシピ大量データでBERTをファインチューニングしたRecipeBERT
    huggingface.co
    huggingface.co
    は食品名と材料・レシピの知識を反映したベクトルを生成します。ドメイン特化モデルは一般的に限定的な語彙での同義表現に強く、食品名マッチング精度向上が期待できます。ただし汎用モデルに比べ公開例が少なく、追加の学習コストが発生する点に留意してください。

    多言語対応の検討: USDAデータベースが英語表記である場合、クエリが日本語など他言語になる可能性も考慮します。その場合、多言語版Sentence-BERT（例：paraphrase-multilingual-MiniLM-L12-v2）を利用すれば、異言語間でも共通のベクトル空間にマッピングでき、クエリを直接多言語対応ベクトル検索できます。あるいは事前にクエリを英訳する前処理を挟む方法もあります。

推奨モデル: 最初の実装では扱いやすさと性能バランスから汎用の事前学習Sentence-Transformerモデル（例えばall-MiniLM-L6-v2）を採用することを推奨します。まずはこれで十分な精度が得られる可能性が高く、後述の評価で精度不足が判明した場合に食品特化モデルやファインチューニングの追加検討を行います。
ベクトルインデックスと類似検索手法

候補検索には高速な近似最近傍（ANN: Approximate Nearest Neighbor）検索を用います。ベクトル化モデルでオフラインにデータベース内全食品エントリの埋め込みベクトルを計算し、ANNインデックスに格納しておきます。データ規模（最大1万件）であれば線形検索でも100ms以下で処理可能ですが、今後の拡張も見据えANNライブラリを利用します。

    インデックス構築: Facebook製のFaissが高性能かつ広く使われるANNライブラリです。LSHやHNSW法に対応しており、本件規模では内蔵のIndexFlatIP（コサイン類似度に相当）で十分高速です。Faissにベクトルを追加する際、ベクトルの正規化（コサイン類似度をそのまま内積で計算するため）を行います。また、初期段階では精度重視でExact Search（HNSWのM小さめ、またはFlat index）設定とし、開発段階の評価で問題なければ本番も簡易に運用できます。より大規模になればHNSW（IndexHNSWFlat）で近似検索のスピードアップを図ります。

    類似度スコア: クエリとエントリのコサイン類似度をスコアとし、上位K件（要求では5〜10件）のエントリを取得します。Kは後段LLMの負荷と照らして調整可能です。上位候補数が10件程度であれば、この段階の計算量・データ転送量は小さく、リアルタイム処理でも数ミリ秒～数十ミリ秒程度の応答が期待できます。

    候補エントリ情報: インデックスから得られるのはエントリIDとベクトルのみのため、ユーザー提示用やLLM評価用にエントリ名や関連情報を別途保持・取得します。例えば、データベースからエントリ名（食品名）やカテゴリ、説明文を取り出し、後段で使用します。ベクトル検索では略称・スペルミスなどもある程度吸収できますが、食品名の別名（別称）がDBに存在する場合はエントリに同義語フィールドを設けて統合ベクトル化するとより網羅的です。

LLM再ランキング（第2段階）
LLMモデルの選定（オープンソース）

ベクトル検索後の候補から最適な1件を選ぶには、各候補のクエリに対する適合度をより深く評価するLLMを用います
deepinfra.com
。本システムでは外部APIを使わずオープンソースのLLMをインストールして用いる方針です。モデル選定のポイントは、「十分な言語理解による意味比較ができること」と「推論速度（リアルタイム応答可能）」のバランスです。

考えられるアプローチは以下の通りです。

    (A) クロスエンコーダ型モデルによるスコアリング: 事前学習済みの再ランキング専用モデルを使い、クエリと候補をペアで入力して関連度スコアを直接算出する方法です。Sentence-TransformersにはMS MARCOデータセットで訓練されたクロスエンコーダモデル（例: cross-encoder/ms-marco-MiniLM-L-6-v2）が公開されており、これを利用すると高速に関連度スコアを得られます
    adasci.org
    。クロスエンコーダはBERTベースで数億パラメータ規模ですが、上位10件程度を再評価する用途ならCPUでも実用的な性能です。実際、クロスエンコーダで検索結果を再ランクすることで「最も適した回答」を上位に持ってくることができ、検索精度の向上に寄与したとの報告があります
    adasci.org
    。クロスエンコーダはLLMと比べモデルが小さい分応答も速く、リアルタイム性が高いです。

    (B) ジェネレーティブLLMによるリスト再ランキング: ChatGPTのような大規模言語モデルにプロンプトを与え、候補リストからベストマッチを選ばせる方法です。LLMの文脈理解力をそのまま再ランキング問題に応用できます
    medium.com
    。例えば7B〜13B程度のLoRAチューニング済みモデル（Meta社のLlama2系やFalcon, OpenAIのGPT互換モデルなど）を利用し、「与えられたクエリに対し候補の中でどれが最も合致するか」を問うプロンプトを設計します。LLMは候補リスト全体を一度に検討し、記述の細かな違いや暗黙の条件も考慮して柔軟な判断が可能です。「LLMベースの再ランカーを使うことで、単純な埋め込み類似性では拾いきれない文脈・意図を反映した結果を得られる」ことが報告されています
    medium.com
    。ただしトレードオフとして推論コストと待ち時間が増大します
    medium.com
    。モデル推論に数百ミリ秒〜数秒を要する場合もあり、ユーザビリティに影響します。そこで実運用では、応答時間との兼ね合いを見つつモデルサイズや量子化手法の調整を行います（例：7Bモデルを4bit量子化しCPU推論する、GPUを用意する、等）。

推奨モデル構成: オープンソースLLMのみで完結させるため、まず(A)のクロスエンコーダ方式をベースラインとして実装することを推奨します。これは実装が比較的容易で高速かつ、公開ベンチマークで実証された精度を持つためです
adasci.org
。その上でさらなる精度向上が必要な場合に(B)のジェネレーティブLLM方式を検討します。後者を導入する際は、例えばmeta-llama/Llama-2-7b-chat-hfやtiiuae/falcon-7b-instructといったモデルを選択し、システムプロンプトとユーザープロンプトを工夫してモデルの判断精度を引き出します。モデルは比較的小型のものを選びつつ、必要であれば知識を補強するため追加のファインチューニングも検討します。いずれの方式でもAPIは不要で、モデルと重みをローカルに配置して利用できます。
再ランキングのプロンプト設計と推論フロー

LLM（生成型）を用いる場合、プロンプトデザインが結果精度に直結します
medium.com
。本システムでは「候補から最適な1件を選ぶ」タスクに特化したプロンプトを与え、不要な出力（ランダムな会話など）を避けます。プロンプト設計上のポイントと例を以下に示します。

    プロンプト形式: **一覧選択型（Listwise）**を採用します。すなわち、LLMに対し「入力クエリと複数候補」を一度に提示し、その中から最も関連性が高い候補を選ぶよう指示します。LLMによる再ランキングのプロンプト手法には、各候補を個別に評価するポイントワイズ、候補を順位付けするリストワイズ、候補同士を順に比較するペアワイズがあります
    fin.ai
    。候補数が少ない本ケースでは、一括で扱えるリストワイズ方式が簡潔で効果的です。また、最終的に1件のみ選べば良いため、LLMの出力もシンプルになります。

    システムプロンプト: モデルが指示に忠実に従うよう、システムメッセージで役割を定義します（対応するAPIやフレームワーク利用時）。例えば「あなたは食品データベース照合システムです。ユーザーから与えられた食品名と説明に最も合致する候補を選択してください。」といった指示を与えます。

    ユーザープロンプト: クエリと候補一覧を明示的に構造化して提示します。例えば以下のような形式です。

    クエリ: {search_name} （説明: {description}）
    候補:
    1. {候補エントリ1の名称} - {候補エントリ1の説明やカテゴリ}
    2. {候補エントリ2の名称} - {候補エントリ2の説明やカテゴリ}
    ...

    各候補には識別子（番号やID）を付与し、LLMには**「上記の候補の中からクエリに最も該当するものを1つ選び、その番号のみを出力してください」**と指示します。このように出力形式を指定することで、モデルが不要な文章を返すのを防ぎます。必要に応じて理由を説明させることも可能ですが、リアルタイム処理では簡潔さを優先します。

    コンテキスト情報: 候補の表記が簡潔すぎて曖昧な場合、データベース内の追加属性（例：食品カテゴリ、成分情報など）があればプロンプトに含めます。例えば「(カテゴリ: 和菓子)」「(材料: 鶏肉)」等を付記することで、LLMが判断しやすくなります。

    出力処理: LLMから返された回答（候補番号または名称）をパースし、該当するデータベースエントリを最終結果として返します。万一フォーマットが乱れた場合のロバスト性も考慮し、番号のテキスト抽出や、信頼度低下時のフォールバック（例：スコア2位候補の採用など）も設計上検討します。

実装詳細
前処理とインデックス作成

    データ準備: USDA食品データベースから必要項目（食品名、カテゴリや説明文、栄養素など必要に応じ）を取得します。食品名はそのままでは表記揺れがあるため、テキスト正規化を行います（例：大文字小文字の統一、記号除去、単位表記の統一など）。可能であれば別名/同義語リストを用意し、データベースエントリに統合しておきます。

    ベクトル化: 選定した埋め込みモデル（SentenceTransformer）を用いて各エントリのベクトルを計算・保存します。Python実装ではSentenceTransformerクラスを使い、例えば以下のように行います。

from sentence_transformers import SentenceTransformer
model = SentenceTransformer('sentence-transformers/all-MiniLM-L6-v2')
# 各エントリの名称と説明文を結合してベクトル化
db_entries = [f"{item['name']} - {item['category']}" for item in food_db]
embeddings = model.encode(db_entries, convert_to_numpy=True, normalize_embeddings=True)

上記では食品名とカテゴリを"名称 - カテゴリ"の形式で連結しベクトル化しています（カテゴリなど補助情報も埋め込みに含めることで意味的な手掛かりを増やします）。normalize_embeddings=Trueによりベクトルを正規化し、内積でコサイン類似度相当を計算できるようにします。

ANNインデックス構築: Faissを用いてベクトルインデックスを構築します。簡易な内積近似検索ならIndexFlatIPを使用します。

    import faiss
    d = embeddings.shape[1]  # ベクトル次元
    index = faiss.IndexFlatIP(d)
    index.add(embeddings)  # ベクトルをインデックスに追加

    データ件数が1万程度であればIndexFlatIPで問題ありません。より高速な検索が必要になれば、HNSWを使ったIndexHNSWFlatやIVF索引を検討します（ただし構築に追加時間がかかるため現段階では不要）。

    インデックス構築後、メモリ上に保持してクエリ検索に備えます（1万件程度のベクトルなら数MB〜数十MB規模でメモリ常駐可能です）。

クエリ処理と候補検索

    クエリ受け取り: ユーザーまたは画像認識システムからsearch_name（例：「照り焼きチキン」）とdescription（例：「グリル調理された甘辛ソースの鶏肉」）が入力として与えられます。説明が無い場合もありますが、可能なら画像認識時に得られた付随情報を含めます。

    テキスト前処理: データベース側と同様の前処理をクエリテキストにも行います。例えば日本語を英語に翻訳する処理や、カタカナ表記ゆれの正規化（「フライドポテト」→「フレンチフライ」など）が該当します。必要ならルールベースまたは追加の言語モデルで補助します。

    クエリベクトル化: 前処理済みクエリ文字列（例：「照り焼きチキン - グリル 調理 甘辛 ソース 鶏肉」）を、データベースエントリと同じ手順でSentenceTransformerモデルに入力しベクトルを取得します。先に正規化済みモデルならそのまま使えますが、正規化していない場合はクエリベクトル取得後にfaiss.normalize_L2(query_vec)で正規化します。

    近傍ベクトル検索: Faissインデックスに対し、クエリベクトルで内積検索を行います。例えば:

    k = 10  # 上位10件を取得
    distances, indices = index.search(query_vec.reshape(1, -1), k)

    ここでindicesに上位候補エントリのインデックス（データベース上のIDに対応）が、distancesにそれぞれの類似度スコア（内積値）が格納されます。内積値が高いほどクエリとの意味的類似度が高いことを示します。必要に応じてdistancesを0〜1のスケールに変換して扱います。

    候補エントリ取得: 得られたインデックスを元に、元の食品データベースから候補エントリの詳細情報を取得します。名前、カテゴリ、簡単な説明文など再ランキングに必要な情報を取り出しリスト化します。

    例: 上位3件の候補が["照り焼きチキン丼", "グリルドチキン", "親子丼"]だった場合、それぞれにデータベースから詳細説明（例えば栄養カテゴリや類似料理名）を付加し、LLMに渡すリストを作成します。

LLMによる再ランキング処理

    LLM入力構築: 前述のプロンプト設計に従い、クエリ内容と候補リストをテキスト形式で組み立てます。例えば:

クエリ: 照り焼きチキン（説明: 甘辛いタレでグリルした鶏肉料理）
候補:
1. 照り焼きチキン丼 - 鶏肉を甘辛ダレで焼き、ご飯に乗せた丼物。
2. グリルドチキン - 鶏肉をグリルした料理。タレなしのプレーンな味付け。
3. 親子丼 - 鶏肉と卵を煮込んでご飯に乗せた和風の丼物。
最もクエリに合致する候補の番号のみを教えてください。

このように日本語で与えてもよいですが、LLMモデルが英語の方が性能を発揮する場合は同様の内容を英語で記述します（例: "Query: Teriyaki Chicken (grilled chicken with sweet soy sauce)... Candidates: 1. Teriyaki Chicken Rice Bowl - ..."}。

モデル推論実行: OpenAIのAPIは使わずローカルのモデル推論を行います。PythonではHugging Face Transformersライブラリを用いてモデルをロードしgenerate関数でテキスト生成します。例えばLlama2 7Bの場合:

from transformers import AutoTokenizer, AutoModelForCausalLM
model_name = "meta-llama/Llama-2-7b-chat-hf"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, device_map="auto")  # GPU利用
prompt = generate_prompt(query, candidates)  # 上述の形式でプロンプト文字列を用意
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
outputs = model.generate(**inputs, max_new_tokens=50, temperature=0.0)
result_text = tokenizer.decode(outputs[0], skip_special_tokens=True)

ここでgenerate_promptはクエリと候補からプロンプト文字列を組み立てるユーザー定義関数とします。またtemperature=0.0と設定し、生成のランダム性を排除して決定論的な出力を得ます（毎回同じ質問に同じ答えを返すことを期待）。出力結果の例としてモデルが「1」と返したら、それが最終選択肢です。

※クロスエンコーダ方式(A)を採る場合は上記の生成プロセスは不要です。代わりにCrossEncoderを使いクエリと各候補のペアを入力してスコアを取得します
adasci.org
。例えば:

    from sentence_transformers import CrossEncoder
    cross_encoder = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')
    pairs = [[query_text, cand["name"]] for cand in candidates]
    scores = cross_encoder.predict(pairs)
    best_idx = int(np.argmax(scores))

    そしてbest_idxに対応する候補を選ぶだけです。こちらの方法ではモデルが直接スコアを出すため追加のテキスト解析は不要ですが、得られるスコアは相対値なので閾値設定等で「自信度」が低いケースの検出も可能です。

    結果の取得: LLM（またはクロスエンコーダ）の判断により選ばれた候補エントリを最終的なマッチング結果とします。これにはエントリIDや名称、必要なら他の情報も含めて出力します。例えばシステムの応答として「照り焼きチキン丼（Food ID:12345）」のようにユーザーや上位アプリケーションに返します。

    リアルタイム処理考慮: 上記ステップは概ね数百ミリ秒〜1秒程度で完了する想定です。ベクトル検索は非常に高速（<10ms）であり、LLM再ランキングも候補が少なければ高速です
    deepinfra.com
    。それでも遅延が問題となる場合、以下の対策を検討します:

Pythonコード例

以下に、本システムの主要部分のPython実装例を示します（Sentence-Transformers + Faiss + オープンソースLLMを使用）。

# 必要なライブラリのインポート
from sentence_transformers import SentenceTransformer, CrossEncoder
import faiss
import numpy as np
from transformers import AutoTokenizer, AutoModelForCausalLM

# 1. ベクトル埋め込みモデルとクロスエンコーダモデルのロード
embed_model = SentenceTransformer('sentence-transformers/all-MiniLM-L6-v2')
rerank_model = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')  # オープンソースの再ランクモデル

# （代替案）LLMモデルを使用する場合のロード例:
# llm_tokenizer = AutoTokenizer.from_pretrained('tiiuae/falcon-7b-instruct')
# llm_model = AutoModelForCausalLM.from_pretrained('tiiuae/falcon-7b-instruct', device_map='auto')

# 2. USDA食品データベースのエントリをベクトル化してFaissインデックスを構築
food_names = [entry['name'] for entry in food_db]  # データベース中の全食品名リスト
# ベクトル化（名称と説明を連結して変換）
embeddings = embed_model.encode(food_names, normalize_embeddings=True)
d = embeddings.shape[1]
index = faiss.IndexFlatIP(d)
index.add(embeddings)

# 3. クエリの処理と検索
def find_best_match(search_name: str, description: str = ""):
    # クエリ文字列の準備
    query_text = f"{search_name} {description}"
    # クエリをベクトルにエンコード
    query_vec = embed_model.encode([query_text], normalize_embeddings=True)
    # 上位5件を検索
    D, I = index.search(query_vec, k=5)
    top5_indices = I[0]  # 上位5件のインデックス
    candidates = [food_db[i] for i in top5_indices]
    
    # 4. クロスエンコーダで再ランキング（各候補にスコア付与）
    pairs = [[query_text, cand['name']] for cand in candidates]
    scores = rerank_model.predict(pairs)  # 各候補への関連度スコア:contentReference[oaicite:18]{index=18}
    best_idx = int(np.argmax(scores))
    best_match = candidates[best_idx]
    return best_match

# テスト例
result = find_best_match("Teriyaki Chicken", "grilled with sweet sauce")
print("Best match:", result['name'], "ID:", result['id'])
# 出力例: Best match: Teriyaki Chicken Bowl ID: 12345

上記コードでは、まず食品データベース全エントリを埋め込み、Faissでインデックス化しています。find_best_match関数ではクエリをエンコードし、Faissで類似上位5件を取得、その候補に対しクロスエンコーダモデルでスコア評価して最も高スコアのものを返しています。
adasci.org
に示すように、CrossEncoder.predictにクエリと候補のペアを渡すと関連度スコアの配列が得られます。このようにして最終候補1件を選出しています。

※生成型LLMを用いる場合、上記のrerank_model.predict部分を差し替えます。例えばllm_model.generate()を用いてプロンプトを与え、結果として得られた番号からbest_matchを決定します。クロスエンコーダ方式は実装とデプロイが容易なためまず採用し、精度改善が必要になった段階でLLM方式への切り替えや統合を行うのが現実的です。
評価方法と精度検証

システムの精度評価は、可能であれば既知の正解ペアを用いて行います。例えば、いくつかのテスト画像について正しい食品名とデータベースIDの対応リストを作成し、システム出力との一致率（Top-1精度）を測定します。加えて、上位K候補に正解が含まれている率（Recall@K）も計測し、再ランキング前後での違いを分析します。

評価指標としては、情報検索分野で一般的な**MRR（平均ランキング不偏）やNDCG（正規化割引累積利得）**などのランキング精度指標も参考になります
medium.com
。例えば再ランキング導入前後でNDCG@5がどれだけ向上したかを見ることで効果を定量化できます。また、LLMを用いる場合は上位5候補中から正解を選べているか（Precision@5）に注目することで、LLM部分の挙動を評価できます
medium.com
。

速度評価: 1クエリ当たりの処理時間を計測し、リアルタイム要件を満たすか検証します。目安としては、ベクトル検索はほぼ無視できる高速さですが、LLM推論部分がGPU使用時で数百ms以内、CPUのみでは1秒以内程度に収まるか確認します。負荷テストを行い、QPS（毎秒クエリ数）に対するスケーラビリティも測定します。

モデル評価: クロスエンコーダ方式とLLM方式の両方を試し、精度とレスポンスのトレードオフを評価します。もしオープンソースLLM（例: 7Bモデル）でクロスエンコーダ以上の精度向上が得られず遅延だけが増えるようなら、クロスエンコーダ方式を本番採用し、将来的にモデル改良や知識統合（例えば食品ペアでの追加学習）を検討します。一方でLLM方式が明らかに精度向上をもたらす場合、コストを許容できる範囲で採用します
medium.com
。例えば高精度だが遅いモデルは重要クエリにのみ使い、通常は軽量モデルで処理するといったハイブリッド運用も選択肢です
